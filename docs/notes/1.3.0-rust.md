# 1.3.0 rust: what the docs must say

The owner asked for Rust in one part of Lifetime, kept friendly to a team of Python programmers. It is one small,
optional, server-only accelerator; Python stays the reference and is always there.

## Release notes (for the Lifetime 1.3.0 section)

- The server packages (Windows server package, Linux server `.tar.gz` for x86_64 and aarch64) contain a small Rust
  accelerator, `lifetime_fast`, for the fleet's uptime bars and availability. Results are exactly the same as before.
  `server_info` has a new field `availability_engine`: `Rust accelerator`, `Python`, or
  `Python (Rust accelerator out of date)` when an installed build does not match this version's Python.
- Nothing changes for computers: the desktop app, the agent, source installs and the container image do not contain
  it and use the Python version.

## What it does

`lifetime_availability._sums` is the part of the availability computation that walks every computer's online/offline
intervals: `_subtract`, `_intersect`, `_spread` (seconds per day/week/month bar) and `outages`.
`rust/lifetime_fast/src/lib.rs` is a line-by-line copy of those four functions and `_sums`, with comments naming the
Python line each one copies. Times go over as whole microseconds since 1970 (exact; a Python datetime has
microseconds) and the seconds come back as the same floats Python computes, added in the same order, so every result
is identical, not just close. Everything else (database, time zones, schedules, rounding, coverage) stays in Python.

How the server chooses (`lifetime_availability.py`, top): `import lifetime_fast`; if that fails, or
`LIFETIME_NO_RUST=1` is set, or the module's `API` number differs from `lifetime_availability.RUST_API` (a build
older or newer than the Python), the Python functions run. If the Rust copy ever fails during a computation (a Rust
panic arrives as a Python `PanicException`), that computation is done again in Python, and the server prints one line
"the Rust accelerator failed" to its log the first time.

## Where the time goes (measured on the development PC, 24 November 2026, Python 3.12, synthetic data)

500 computers, an online/offline change every 1 to 15 hours for 400 days (600,000 presence intervals), Last 12
months as 365 daily bars, `uptime_bars` through the real monitoring database:

| Part | Time |
|---|---|
| Whole `uptime_bars` request | 2.4 s (daily bars), 1.7 s (weekly) |
| Reading presence from SQLite and turning its text times into datetimes (`lifetime_monitor._device_availability`, `_time`) | about 1.5 s |
| `device_availability` for all 500 | 0.8 s |
| of which `_sums` (the part in Rust) | 0.45 s |
| converting its datetimes to microseconds for Rust | 0.17 s |

cProfile put `_spread`, `_intersect` and `outages` at the top of `lifetime_availability`, so those (with
`_subtract`, which sits between them) are what moved to Rust. `normalize`, `_merge` and `local_midnight` stay Python.

The Rust time itself could not be measured here (no Rust on this PC). **Measured in CI**: the test job runs
`python tools/availability_speed.py`, which prints both engines' time for the same 500 computers x 365 days and checks
the results are identical; read the numbers from the `rust-accelerator` job, step "Compare with the Python reference,
then forced to Python, then the speed of both" (Windows and Ubuntu). Expected:
`device_availability` about 0.8 s -> 0.55 s, so the whole `uptime_bars` request about 10% faster. The largest cost,
reading and parsing the presence history from the database, is untouched; if the bars must be faster, that is the next
place to look (in Python first).

## How to build it locally, and how to turn it off

Needs Rust 1.91.0 (rustup) and maturin 1.10.2:

```sh
python -m pip install maturin==1.10.2
python -m maturin build --release --locked -m rust/lifetime_fast/Cargo.toml --out build/rust-wheels
python -m pip install --force-reinstall --no-deps --no-index --find-links=build/rust-wheels lifetime_fast==0.1.0
```

(In a virtual environment: `pip install maturin==1.10.2 && maturin develop -m rust/lifetime_fast/Cargo.toml`;
`maturin develop` refuses to run outside one.) Turn it off: `LIFETIME_NO_RUST=1` in the server's environment, or
`python -m pip uninstall lifetime_fast` for a source install.

Building packages: `build_server_windows.ps1 -WithRust` (needs Rust; fails if the runtime ends up without it);
`LIFETIME_RUST=1` for `packaging/linux/build_linux.sh build` (installs rustup-init 1.28.2, checked against its
recorded sha256, and Rust 1.91.0 inside the Rocky Linux 8 container). Without those the packages are built as before,
with the Python version. CI always builds with them.

## CI (what it checks)

- The Python `test` matrix (Windows Server 2022/2025, Ubuntu; Python 3.11 and 3.12) never builds or needs Rust; there
  `test_availability_engines` checks the Python and skips the Rust half.
- Job `rust-accelerator` (Windows with Python 3.12, Ubuntu with 3.11): checks `Cargo.lock` (if it does not match, the
  log shows the smallest change cargo wants), builds with Rust 1.91.0 and maturin 1.10.2 (`--locked`), then runs
  `test_availability_engines`, `test_availability`, `test_monitor` with it (`LIFETIME_REQUIRE_RUST=1`: the comparison
  may not be skipped), `test_availability_engines` and `test_availability` again with `LIFETIME_NO_RUST=1`, and the
  speed tool. Only `windows-server-package`, `linux-build` and `release` wait for it; the Python tests and the Windows
  desktop/agent package never do. (`linux-build` also makes the Linux desktop AppImage, in the same job as the server
  bundle, so a Rust failure does stop that artifact; see "How to ship without Rust".)
- Windows server package: built with `-WithRust`; the build fails if `lifetime_fast` is not inside
  LifetimeServerRuntime.exe (checked in PyInstaller's PKG-00.toc), and a following step starts the packaged runtime and
  fails unless `server_info` says `Rust accelerator`. Without `-WithRust` the script never bundles it, even when an
  older build is installed on that PC. LifetimeServerDashboard gets it too (it never
  computes availability itself, but the brief asked for it and Windows Server is not affected by Smart App Control);
  LifetimeAgent is built with `--exclude-module lifetime_fast`.
- Linux bundles: built with `LIFETIME_RUST=1` in Rocky Linux 8 (glibc 2.28) for x86_64 and aarch64; the build fails if
  the server bundle lacks it. The smoke test on 11 distributions asks the running packaged server for
  `availability_engine` and fails unless it is `Rust accelerator` (x86_64 only: aarch64 has only the file check).
  Desktop programs on Linux exclude it, and so does the Linux server dashboard, because it lives in the desktop
  bundle.
- `build_windows.ps1` (desktop) excludes it too, so a developer who installed it can never ship it in the desktop app.

## SECURITY

- Server only. Native code is never added to the desktop app or the agent (Windows 11 Smart App Control blocks
  unsigned native files on employee PCs). On Windows Server and Linux this does not apply.
- It reads only numbers the server already computed from its own database; it never sees what computers send.
  A panic inside it becomes a Python exception; the server then does that computation in Python and logs the
  failure once. It never crashes the server.
- Exact versions: Rust 1.91.0, maturin 1.10.2, PyO3 0.27.2 and every crate pinned with a checksum in
  `rust/lifetime_fast/Cargo.lock`; rustup-init downloads are checked against a recorded sha256. Licenses are MIT OR
  Apache-2.0 (added to THIRD_PARTY_NOTICES.md).

## Not tested / known limits

- **Nothing in Rust was compiled or run on the development PC** (Rust may not be installed there). The first CI run
  must confirm: it compiles on Windows x64 and Linux x86_64/aarch64 with Rust 1.91.0; `Cargo.lock` (written by hand
  from the crates.io index, since cargo was not available; a reviewer checked it against the index) is accepted by
  `--locked` (if not, the CI log prints the change to commit); the comparison test passes; the packaged Windows
  runtime starts and reports `Rust accelerator`; the speed-up.
- The wiring was tested here with a Python stand-in that copies `lib.rs` line by line on integer microseconds: all
  comparison cases were identical, and a deliberate one-in-a-billion change in it was caught.
- Exact equality holds for any single interval shorter than 285 years (2^53 microseconds); periods are at most 3,660
  days.
- No Windows ARM64 server package exists, so none is built for it.

## How to ship without Rust

A Python-only team is never blocked. A change to the Python is always safe: change it, and the comparison test in the
`rust-accelerator` job tells you whether `rust/lifetime_fast/src/lib.rs` must follow (the failure names the file, and
the Rust function has the same name). If nobody can change the Rust, or Rust breaks, release without it by editing
`.github/workflows/windows.yml` and one script:

1. `windows-server-package`: change `./build_server_windows.ps1 -WithRust` to `./build_server_windows.ps1`, and delete
   the steps "Rust 1.91.0 for the server's accelerator" and "The packaged runtime loads the Rust accelerator".
2. `linux-build`: delete `-e LIFETIME_RUST=1` from the `docker run` line.
3. `packaging/linux/smoke_test.sh`: delete the three lines after "The packaged server loads its Rust accelerator"
   (`engine=...`, `echo ...` and the check that fails unless it says `Rust accelerator`).
4. Remove `rust-accelerator` from `needs:` of `linux-build`, `windows-server-package` and `release` (and, if you like,
   delete the whole `rust-accelerator` job).

The packages are then built as before 1.3.0, with the Python version and the same results. To bring Rust back, undo
those lines.
- `docs/UPGRADE_PLAN.md` ("Rust: only where it is measured to help", rule 4: only after releases are code-signed)
  should say that the owner allowed this server-only exception for 1.3.0, and give the CI-measured speed.
