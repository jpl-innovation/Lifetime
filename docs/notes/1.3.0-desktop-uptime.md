# 1.3.0 desktop uptime: what the docs must say

Worker 3 (desktop uptime), branch `w3-desktop-uptime`. Text for the lead to merge into README, RELEASE_NOTES
("Next release"), SECURITY and SERVER_OPERATIONS. Plain words, as users read them.

## For the release notes

- **Choose any date range.** Activity and Reports have one date picker: Today, Last 7 days, Last 30 days, This month,
  Last month, This year, Last 12 months, Last 5 years, All, or Custom with From and To calendars. From has no lower
  limit; To cannot be in the future. The choice is remembered. Every chart and total on Activity follows it, and
  Export report starts on the same period.
- **Days with no record are unknown, never zero.** A line under the title says where the data starts, for example
  "Data from 3 Jul 2026 (Windows log) · recorded by Lifetime since 6 Nov 2026 · no archived logs found".
- **New page: Uptime & downtime** (Vietnamese: "Thời gian hoạt động"), in the sidebar after Activity, shown when
  history is on. For the chosen range it shows:
  - totals: awake, asleep, off (shut down or restarting), unknown (no record), and the awake share of known time;
  - counts: restarts, shutdowns, unexpected stops, average awake time between unexpected stops, longest continuous
    awake and longest off;
  - each day: one row per day for up to a month, or one stacked bar per day for longer ranges, with a red mark on
    days with an unexpected stop;
  - the power events (started, shut down, restarted with who or what asked, slept, woke with the wake source,
    unexpected stop), newest first, 50 at a time with "Show more".
- **Downtime history.** Lifetime now keeps, per day, the time asleep, off and unknown, and how many restarts,
  shutdowns and unexpected stops there were. It reads them from the Windows System log (or the Linux journal) in
  the background about once an hour, and "Add earlier usage" fills in the past from the same log.
- **More of the past, where the computer still has it:** Lifetime also reads archived System logs
  (`Archive-System-*.evtx`, kept when IT sets the System log to "archive when full") and, on Linux, the rotated
  login records (`/var/log/wtmp.1`, `wtmp.*.gz`). If they are missing or cannot be read, nothing fails; the
  coverage line says so.
- **Who restarted the computer.** Windows event 1074 now tells which program or account asked for a shutdown or
  restart, and why. It is shown in the event list only.
- **Reports** (PDF and CSV) have a new "Uptime and downtime" section with the same totals and counts for the chosen
  period, and where the data starts.
- **Daily awake totals are kept for 10 years** (was 400 days), so "Last 5 years" shows real days as history builds
  up. Hourly detail is still kept for 400 days.
- **Connected computers** send the per-day downtime to a server that says it accepts it (the `downtime`
  capability), only when history sharing is on. Older servers never receive it; older computers never send it.

## How the numbers are worked out (README, "How this is counted")

- Uptime is awake time, as before. Off time is split into asleep (sleep or hibernation), off (shut down or
  restarting) and unknown (no record). Awake time itself is unchanged: downtime never changes it.
- A clean stop followed by a start within 10 minutes is a restart; a longer gap is a shutdown. When Windows logged
  who asked (event 1074) and the type is in English ("restart", "power off"), that type wins. On other Windows
  languages the 10-minute rule decides.
- "Shut down" with Windows Fast Startup is really a hibernation. When a shutdown request (1074) is followed within
  two minutes by hibernation, Lifetime counts that time as off and the shutdown as a shutdown, not as sleep.
- An unexpected stop is Kernel-Power 41 or EventLog 6008 at the next start (the two describe the same stop and are
  counted once). On Linux there is no such event: an end that neither the journal nor the login records show as a
  clean shutdown counts as an unexpected stop, and a "crash" entry in the login records too.
- After an unexpected stop, the time until the next start is unknown: nothing says when the computer stopped.
- Boots known only from the rotated Linux login records have no sleep records: their gaps count as off and in the
  counts, their running time stays unknown.
- "Average awake time between unexpected stops" is awake time in the range divided by the number of unexpected
  stops. Longest spans need the event list (read from the log when the page opens); without it they say
  "Not available".

## The honest limits (README and SECURITY "what is not verified")

- Windows keeps only what fits in its System log (on the development PC: back to 3 July 2026, about 4.5 months).
  Days before that are unknown unless archived logs exist. Lifetime never changes the log size; IT can raise it by
  group policy.
- The event list is read from the system log each time the page is opened (at most every 10 minutes); it is never
  saved and never sent. Names and accounts from event 1074 appear only there.
- A computer that cannot read its System log (or a Linux user without journal access) has no downtime; the coverage
  line says "the system log could not be read".
- Not verified on real machines: archived System logs on a computer that really archives (the tests use
  recorded-shape data; reading an `.evtx` with `wevtutil /lf:true` was checked once by hand with a file exported
  from the development PC's own log, not in a committed test), non-English Windows (1074 type words), real rotated
  and gzip wtmp files on Linux (tested with synthetic `last` output), Fast Startup detection beyond the development
  PC, how long the Linux event list takes to read with many boots, a ledger with years of real history, and the
  server side of the `downtime` capability (built by the server work; tested here against a simulated server).
- Measured on the development PC with 1,900 synthetic days: the Uptime & downtime page computes and paints in about
  40-90 ms; the window's once-a-second refresh, reading a real 540 KB ledger and status file, takes about 16-19 ms.
  The filtered System log read takes about 0.2 s.

## For SECURITY.md

- New ledger keys `downtime_daily` (numbers only: seconds and counts per local day) and `downtime_sources` (which
  log was read, how many archived logs, from which date; no paths, names or accounts). Both are dated history and
  follow the History consent: not written, shown, reported or sent when history is off; removed from the machine
  agent's ledger when history sharing is turned off; removed by "Delete history" with the rest of the ledger.
- The machine agent reads the power log in the background only while its reporting loop runs and history sharing
  is on. The client adds `history.downtime_daily` only for servers that advertise `downtime`.
- Older versions still open a 1.3.0 ledger (they ignore the new keys; tested with the 1.2.1 validator), and 1.3.0
  opens a ledger without them.

## For SERVER_OPERATIONS.md (client side only)

- A computer running 1.3.0 sends `history.downtime_daily` (at most 3,660 days, the contract shape) only after the
  server lists `downtime` in its capabilities. If the server answers 400, the computer sends the 1.1 format for a
  day, as for the other optional parts. If the message would pass 1 MB, the oldest days are left out.
